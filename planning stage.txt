## 결정난 사항 - 적재
1. 사전 적재    초록 위주의 공용 논문 풀을 구축
    상위 n% 이내의 논문들은 전문을, 나머지는 제목과 초록을 적재

2. 키워드 추가 시    풀에서 즉시 검색하고, 결과가 적으면(여러 테스트를 통해 결정) 해당 키워드 논문을 추가 수집
    이렇게 되면, 많은 사용자가 수많은 키워드를 추가하였을 때 너무 많은 추가 수집(db 수정)이 일어나지 않을까 하는 우려
    -> 추가 수집 결정된 논문들의 메타데이터를 우선적으로 DB에 저장하고, 임베딩 할 내용들을 대기열에 넣는다.
        야간에 한번에 대기열을 임베딩하며 db 갱신

3. 발송 결정 시 (비동기)    발송 논문 전문 + 레퍼런스 전체의 제목·초록 + 중요 레퍼런스 상위 n편(디테일 필요) 전문
    저장할 논문이 사전 적재된 논문과 중복되는지, 중복되면 전문으로 저장됐었는지 초록이었는지, 동일하면 추가적재X, 초록이면 초록 버리고 전문

    발송 논문 전문을 읽고, 언급 내용이 가장 많은 or 핵심 내용에서 언급하는? 논문이 중요
    핵심 내용: 논문을 작성하게된 결정적 계기, 방법론에서의 진화 or 참고

    항목	점수	기준
    isInfluential	40	true면 40, false면 0
    언급 수	최대 25	1회당 5점, 5회 상한
    문맥 표현	최대 20	직접 기반 20, 방법론 사용 10, 비교·배경 0
    발송 논문과의 유사도	최대 10	max(cos, 0) × 10
    Dataset, Benchmark, Corpus 감점	-35	제목에 단어로 포함될 때
    
    isInfluential을 알 수 없으면 나머지 항목의 만점이 55점이 되므로, 점수에 95/55를 곱해 환산합니다.

    브리핑 저장 위치
    브리핑은 벡터 DB에 넣지 않습니다. 유사도로 찾는 자료가 아니라 paper_id로 바로 꺼내 쓰는 자료이기 때문입니다.

    사용자별로 저장할 필요도 없습니다. 같은 논문의 브리핑은 받는 사람이 달라도 같아서, 사용자별로 저장하면 생성 비용과 저장 공간만 늘어납니다. 사용자와 논문의 연결은 기존 sent_papers가 맡습니다.

    데이터	단위	저장 위치
    논문 청크와 임베딩	논문별	벡터 DB
    브리핑	논문별	관계형 DB
    본 논문 → 레퍼런스 관계	논문별	관계형 DB
    발송 이력	사용자별	관계형 DB(sent_papers)
    대화 기록(저장한다면)	사용자별	관계형 DB



## 결정난 사항 - 에이전트

'''
논문 분석 에이전트 (본 논문에 관한 질문)
    
    본 논문 안에서만 검색합니다.

    기본 자료: 새벽에 만든 브리핑(문제, 방법, 기여, 한계)을 항상 답변 자료로 넣습니다.
    검색 단위: 전문을 섹션 경계에 맞춰 나눕니다. 표와 수식은 주변 설명과 같은 청크에 둡니다.
    섹션 필터: 질문 유형에 맞는 섹션의 점수를 높입니다. 결과 질문은 Results와 Experiments, 방법 질문은 Method입니다. 섹션을 제외하지는 않으므로 이름이 달라도 결과가 사라지지 않습니다.
    수치 질문: 표와 수치는 임베딩 검색이 놓치기 쉬워서 BM25를 함께 씁니다.

RAG 에이전트
    메타데이터 필터링: 정규화된 키워드와 모드별 제외 조건으로 후보를 줄입니다.
    병렬 검색: 후보에 벡터 검색과 BM25를 각각 실행합니다.
    결과 결합: Reciprocal Rank Fusion으로 합쳐 상위 5~8개를 넘깁니다(잠정값).
    필터 완화: 결과가 너무 적으면 키워드 필터를 빼고 다시 검색합니다. 정규화가 잘못되어도 결과가 전부 사라지지 않게 하기 위해서입니다.

통합 에이전트 (전체 통합)
    답변 단계에서는 받은 근거만으로 답하고, 본 논문 내용, 다른 논문 근거, 일반 설명을 구분해 표시합니다.
'''





근거가 부족할 때
    재검색: 결과가 없거나 관련도 점수가 낮으면 쿼리를 넓혀 1회만 다시 검색합니다. 이 재작성은 LLM 없이 필터 완화로 처리해 호출 수를 늘리지 않습니다.
    솔직한 답변: 그래도 없으면 "공용 풀에서 찾지 못했다"고 말합니다. 일반 지식으로 설명하더라도 출처가 없다고 표시하고, 논문을 지어내지 못하게 합니다.
    수집 연결: 검색에 실패한 쿼리를 기록합니다. 자주 실패하는 주제는 기존 기획의 야간 수집 대기열로 넘기면 풀이 실제 수요에 맞춰 채워집니다.

신뢰도 향상을 위함
    후속 연구처럼 최신 논문이 필요한 질문은 풀이 갱신된 시점까지만 답할 수 있으므로, 답변에 검색 범위를 밝히는 것이 좋습니다.
    ex) arxiv에서 00년 00월 ~ 00년 00월 까지의 논문 확인 결과, 답변과 관련된 논문을 찾기 어려웠어요 ㅠㅠ
